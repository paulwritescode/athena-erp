# Architecture overview

**Last updated:** 2026-11-20
**Status:** Core-platform direction accepted; implementation has started with the pinned pnpm toolchain. Vocabulary follows ADR-0008 (Proposed).

## Product intent

Athena is the reusable core on which different ERP products and business packs can be built. It is not currently an ERP configured for one industry, country, or company. The core provides the runtime, data model, permissions, API, rules, and module boundaries; domain-specific Record Types and Packs are added on top.

## Runtime shape

```text
Browser
  └── one origin / one Go process (:3000 by default)
      ├── Vue 3 + TypeScript + Vite frontend, embedded at build time
      ├── ConnectRPC API and generated Protobuf clients
      ├── MariaDB metadata and per-Record-Type tables
      └── optional generated Go behavior compiled into the server
```

- `make run` builds the Vite application and starts Go on loopback at port `3000` against `ATHENA_DATABASE_URL` (development).
- `athena init` creates a home with the database server login; `athena new` creates a Workspace folder and its own database named from the slug; `athena run` serves one Workspace, checks the database's `athena_workspace` ID against `athena.yaml`, and holds a per-user lock so only one Workspace runs at a time. See [ADR-0004](../decisions/adr-0004-project-per-database.md).
- `make build` embeds the built frontend in `bin/athena`.
- ConnectRPC remains the selected Go RPC library and Protobuf remains the intended API contract. Record Types (`RecordTypeService`), Records (`RecordService`), sign-in, users and Roles (`AuthService`) and system info (`SystemService`) all use it; there is no separate JSON API.
- MariaDB is the only relational database being implemented now. PostgreSQL is a later adapter, not a current choice.
- AWS, Cloudflare, identity providers, queues, and object storage remain optional integrations around the core.

## Frontend direction

See [Frontend theme and typography](frontend-theme-and-type.md) for the centralized palette and type scale.

- One supported frontend: Vue 3 + TypeScript + Vite.
- pnpm 11.22.0 is the pinned package manager. `web/pnpm-lock.yaml` is the sole frontend lockfile; `make web-build` uses frozen installation before typecheck/build.
- Primary component system: shadcn-vue, using the existing project's Vite setup.
- The current `components.json` records the requested `aeaM05w` preset output: `reka-luma`, Zinc base tokens, Inter, `0.625rem` base radius, and pointer cursors. The exact command was applied to the existing `web/` app; no replacement frontend was created.
- Theme is class-based and token-driven. A visible toggle follows the operating-system preference on first use and stores an explicit choice in local storage.
- The **Build** desk contains Overview, Record Types, Packs, Rules, and Files. Rules follow `rules:read` and Files `files:read`. **View** lists a saved Record Type's Records and creates, edits and deletes them. The desk opens on a sign-in page; Build is shown to users with the build permission, and View lists the Record Types the user may read. A user menu in the top bar changes the password and signs out.
- The core UI starts without industry-specific sample Record Types or Packs.
- App colors and light/dark semantic tokens live in `web/src/theme.css`; the supplied typography scale lives in `web/src/typography.css`. Buttons use shadcn-vue semantic primary, secondary, outline, ghost, and destructive variants so palette changes flow from the shared theme.

## Domain vocabulary and data model

- A **Record Type** names a data structure, its fields, validation, and behavior hooks. A Record Type maps to a dedicated MariaDB table. A saved **Record** is a row in that table. These terms follow ADR-0008 (Proposed), which supersedes D-005.
- A **Workspace** is a database plus its installed Packs, Records, users and overlays. A **home** is the directory that holds the database server login and the Workspace directories.
- A field has a stable code name, display label, type, and validation attributes. A Link field identifies another Record Type and represents a database relationship.
- New dashboard fields derive a lowercase `snake_case` code name from their label. Reserved names and collisions are disambiguated; the generated name is editable before that field saves and remains stable after a successful save. The editor preserves row identity while names update so typing and pasting do not lose focus.
- A **Pack** is an installable bundle of Record Types, explicit relationships, rules, actions, reports, permissions, and navigation. A **Module** is a functional area inside a Pack and is not implemented.
- Pack relationships must have concrete database meaning: foreign keys for direct links, and join tables for many-to-many relationships when supported. Relationship cardinality and delete/update rules need to be explicit.
- Record Type definitions must be usable from both the dashboard and the codebase. Dashboard-authored definitions are stored in MariaDB. Code-authored definitions live in the repository. Their merge, precedence, upgrade, and export rules remain to be designed.
- Dashboard-authored Record Types are intended to generate Go source scaffolds in the developer/codebase workflow. Saving a Record Type updates metadata and database schema; it does not compile or activate Go code in the running server. The generator, writable destination, and synchronization lifecycle are not implemented.

## Logic boundaries

- Go owns trusted lifecycle code, permission checks, invariants, persistence, and transaction boundaries.
- Starlark is the configurable rule language for conditions and bounded actions. It receives typed Record values and explicit Go-provided capabilities; it does not execute arbitrary SQL or bypass Go enforcement.
- A rule may reference Record Type and field identifiers, and Pack relationships. The rule editor/compiler must validate references against the current definitions.
- A Starlark host exists (`internal/rules`, ADR-0016, Proposed, not production-ready); no Go hook generator is implemented.
- Conditions, formulas and filters use a separate, smaller expression language (`internal/expr`, restricted CEL on cel-go, ADR-0013, Proposed). It is side-effect free, bounded and exact, and Go runs it inside the write transaction. Starlark is not used for them.

## MariaDB persistence

- `ATHENA_DATABASE_URL` configures the Go MySQL driver DSN. When configured, Athena connects at startup and applies system migrations.
- `athena_record_types` stores Record Type definitions. Saving a Record Type provisions `p_workspace__<key>` (the reserved pack name `workspace`, at most 63 bytes, ADR-0009) with an `id`, a `revision`, timestamps, and columns mapped from its fields. Supported field types currently map to MariaDB types in Go.
- Link fields require a known target Record Type and create a foreign-key constraint (`fk_rtype_<hash>`) when its table exists. The relationship editor and Pack composition workflow are not implemented yet.
- Saving a Record Type goes through `RecordTypeService.SaveRecordType`: Go validates the definition, takes a per-database schema lock, checks the expected revision, journals the operation in `athena_record_type_operations`, applies the table changes, then activates the new revision with a compare-and-swap. Pending operations resume at startup.
- A saved Record Type can be deleted with `RecordTypeService.DeleteRecordType`, which drops its table and Records through the same journal and revision check. It is refused while other Record Types link to it, and needs `delete_records` when Records exist. The desk asks for confirmation first; an unsaved Record Type is just discarded. An interrupted delete resumes at startup.
- Each MariaDB DDL statement commits on its own, so the table steps are written to be safe to repeat. If a table change fails, the definition stays at its previous revision and the operation is marked failed with the step and error; tables or columns already created stay and are reused on the next save.
- `RecordTypeService.PlanRecordTypeSave` lists the migration a save would run: adding fields, removing fields (dropping their column and values), changing a field's type or link target (values that cannot convert are counted), and making a field required (empty Records need a fill-in value). `SaveRecordType` refuses a plan that deletes values unless `confirm_data_loss` is set, and a plan that leaves required fields empty unless `backfills` supplies a value. The answers are stored with the journaled operation; every step checks or tolerates current state, so resume is safe. Field and Record Type keys stay fixed after the first save; renaming a key is not supported. In Build, saving a saved Record Type first fetches the plan; if it deletes values or needs fill-in values, a review dialog collects the answers before `SaveRecordType` runs.
- `RecordService` (ConnectRPC) lists, gets, creates, updates and deletes Records. Go loads the saved definition, validates each value by field type, binds every value and takes table and column names only from that definition. Updates and deletes require the Record's current `revision`. Lists use keyset paging on the UUIDv7 `id`, capped at 200 rows, with a cursor bound to the Record Type.
- Each Record create, update, delete, submit and cancel also appends a row to the hash-chained Audit Log (`athena_audit_log`) in the same transaction, listing each changed field with its old and new value, the actor (the signed-in username, or `Local administrator` for the command line), the source and the request ID. `RecordService.ListRecordHistory` returns a Record's rows newest first; `athena audit verify` and `athena audit anchor` checks the chain (ADR-0012).
- System migration 5 (`vocabulary_rename`, ADR-0008 and ADR-0009) renames the tables, columns, indexes, foreign keys and stored keys of a database created before the rename, keeps all row data, and is safe to resume or repeat. It stops with an error naming both tables when an old and a new name exist together.
- Record kinds and system fields (ADR-0010, Proposed): a Record Type has a `kind` (master, document, child or setting), fixed after the first save. The kernel adds `created_by`, `modified_by`, `def_version` and `request_id` to every table, `owner` to masters and documents, `deleted_at` to masters, and `parent_id` and `idx` to children. Deleting a master Record soft-deletes it; a setting holds one Record; a child needs a live parent. Fields can declare `unique`, `default`, `min`, `max`, `pattern`, `max_length`, `read_only`, `set_once` and `index`, enforced in Go and mirrored in `web/src/fieldRules.ts`; `no_copy` is stored only. New types: Money (integer minor units plus fixed currency), Quantity (fixed unit) and Enum. Numbering, ledger and the other kinds are not implemented. Every Record write opens a kernel span carrying only the operation, Record Type key, request ID and outcome code.
- Database sessions run in UTC so `TIMESTAMP` values read back correctly.
- OpenTelemetry is optional and off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set (`internal/telemetry`). The server traces ConnectRPC calls and MariaDB statements (statement text only, no parameter values) and exports metrics. The desk (`web/src/telemetry.ts`) starts tracing when `SystemInfo.telemetry_enabled` is true and posts spans to `/otlp/v1/traces`, which the server forwards to the collector; the server trusts the browser's `traceparent` while it is loopback-only. `make telemetry` runs `grafana/otel-lgtm` locally on 127.0.0.1.
- Every ConnectRPC call passes the permission gate (`internal/server/gate.go`, ADR-0014, Proposed). Only system info, sign-in and the session check are open; everything else needs a session cookie and the `X-CSRF-Token` header, and a Grant or system permission. Authentication is implemented but not reviewed for hosted use; the server stays on loopback.
- Packs, rules, multi-tenancy, audit retention, OIDC and multi-factor sign-in, and backups are not production-ready.

| Record CRUD | Implemented through `RecordService` and the View page, with optimistic revisions and per-Record change history, behind sign-in and Grants (ADR-0014) |
| Authentication and Grants (`internal/auth`, `AuthService`, ADR-0014, Proposed) | Implemented for MariaDB (migration 9): local users with Argon2id hashes, lockout after five failures, opaque database sessions in an HttpOnly SameSite=Strict cookie, an HMAC CSRF header, content security headers and a same-origin check. One deny-by-default ConnectRPC gate covers every procedure. Roles hold system permissions (build, access, audit, files:read, files:write, rules:read, rules:write) and Grants (actions, field permission level, row condition in the expression language, separate duties); row conditions are compiled into list, lookup and read queries; fields above the user's level are left out and masked in history and versions. The sign-in card shows distinct states: no users yet (with the owner command, copy and "Check again"), wrong credentials (one generic toast for a wrong password and an unknown user), a locked or disabled account (revealed only to someone who gave the right password, with the unlock time and `athena user set <name> --unlock`), an ended session, server unreachable, database not connected, a CSRF mismatch and unexpected errors (short text and the request ID). `web/src/apiErrors.ts` maps ConnectRPC codes to these states for every page. Not built: OIDC, multi-factor sign-in, company data scopes, report and export permissions, a desk page for users and Roles. The server still binds to loopback |
| Automated tests | Go tests for `RecordTypeService` and `RecordService` against throwaway MariaDB databases (skipped when `ATHENA_TEST_DATABASE_URL` is unset) and Vitest for `web/src/fieldRules.ts`, both driven by one shared rule table; run with `make test`. No end-to-end browser tests; PostgreSQL is untested |
| Pack composer and relation/join table management | Product direction accepted; implementation pending |
| Workspace files (`internal/files`, `FileService`, `athena files`, ADR-0015, Proposed) | Implemented for MariaDB (migration 10): list, read, create or upload, rename, delete and version history of text files in `record_types/`, `rules/`, `packs/` and `generated/` of the Workspace directory. Paths are confined (no absolute paths, `..`, symbolic links, hidden names or uppercase; every disk access goes through `os.Root`), files are UTF-8 text up to 1 MiB and 1000 files, writes need the content hash the caller read and are atomic, Record Type files are validated with line numbers, and every revision keeps its content. Each change writes an Audit Log row with path, hash and actor, never content. The system permissions `files:read` and `files:write` guard every call. The Files page in Build has a tree, editor, history and a mapping of files to Record Types, Rules and Reports. `.star` files are stored, not run. Needs `athena run` (a Workspace directory); `athena serve` has none |
| Go Record Type source generation | Product direction accepted; destination and conflict rule proposed in ADR-0015; the generator is not built |
| Starlark Rules (`internal/rules`, `RuleService`, `athena rules`, ADR-0016, Proposed) | Implemented for MariaDB (migration 11), **not production-ready**. Validation, derivation, guard and transform Rules in Starlark (`go.starlark.net`) run inside the save through the lifecycle registry, as the acting user, on **document** Record Types. They reach data only through Go host functions (`get`, `find`, `exists`, `set`, `fail`, `warn`, `require`, `log`, exact `decimal` and `money` math); floats, I/O, the clock, `load`, recursion and `while` are refused; a run stops at 200,000 steps or 500 ms, 200 rows read and 50 fields set. Reads follow the user's Grants, row scope and field levels; writes pass the checks of a user's save. A rejection or an error rolls the save back. Every save of a Rule is a version and an Audit Log row (hash, never source); every run is a Rule Run row with the input hash, outcome, counts and request ID, written even when the save is rolled back. `SimulateRule` is a rolled-back dry run with a diff. Not built: a memory limit, posting, reaction and scheduled Rules, `qty` and `fx`, Rules on masters, cascades (nothing can trigger one yet), Rule tests as Records, Rules read from `rules/*.star` files |
| Database dialect layer (`internal/store`) | Implemented for MariaDB only (proposed in ADR-0005): identifier quoting and hash shortening, type mapping, Record Type table DDL and rename statements, upsert, row lock, schema lock, catalogue lookups and error classification. Platform-table DDL now lives in versioned system migrations |
| System migrations (`internal/store/migrate.go`, `server.SystemMigrations`) | Implemented (ADR-0006, accepted; ten migrations; migration 9 adds users, sessions, Roles, Grants and the Access Log; migration 10 adds the Workspace file tables): numbered idempotent steps recorded in `athena_migrations`, applied at start-up and by `athena migrate status/up [--to N] [--dry-run]`; refuses a database newer than the build. Migration 5 applies the vocabulary rename; migration 6 gives existing Record Types the master kind and system columns; migration 8 creates the Audit Log and number counters and moves the old history into the chain. Record Type migrations, key renames, rollback and Pack upgrades are not implemented |
| Document lifecycle (`internal/lifecycle`, ADR-0011, Proposed) | Implemented for MariaDB: a submittable document has `docstate`, `name` and (amendable) `amended_from`; `SubmitRecord`, `CancelRecord` and `AmendRecord` run one transaction each with the event order of spec 5.2, a Document Version snapshot in `athena_document_versions` and a timeline row in `athena_activity` (migration 7). Submitted documents change only in `allow_on_submit` fields; cancel is blocked by a submitted downstream document; Go hooks register on `Kernel.Hooks`. No ledger reversal or workflows yet; Starlark Rules attach to the same events (ADR-0016) |
| Numbering (`internal/numbering`, ADR-0012, Proposed) | Implemented for MariaDB: a submittable document may have a `naming_series` such as `INV-{yyyy}-{#####}`; the next number is taken at submit from a counter row (`athena_number_counters`), inside the transaction for `gap_free` series and outside it otherwise. Names never change once set; `allow_manual_name` lets a create supply an unused name, logged as `name_override`. Only the date scope exists; company and branch scopes wait for P11. Other naming forms are not built |
| Audit Log (`internal/audit`, ADR-0012, Proposed) | Implemented for MariaDB: append-only `athena_audit_log` with `prev_hash` and `hash` per row and a locked chain head (`athena_audit_heads`), written in the change's transaction. `VerifyAuditLog` and `athena audit verify` and `athena audit anchor` detect an edited, inserted, reordered or removed row and a removed tail, and can check an exported `seq:hash` anchor. No masking, retention, partitioning or automatic anchoring; the other logs of spec 12.1 are not built |
| Expressions (`internal/expr`, ADR-0013, Proposed) | Implemented for MariaDB on cel-go: a restricted, exact-decimal language for field `formula` (stored by the kernel in dependency order, cycles refused at save, rollups over child Records recalculated in the child's transaction), `required_if`, `read_only_if`, `validate` and a `depends_on` display hint, all type-checked when a Record Type is saved. `ListRecords` takes a `filter` that is translated to SQL and tested against in-memory evaluation. `PreviewRecord` and `EvaluateExpression` serve the desk and `athena expressions`. Not built: lookup fields, `user`/`setting()` scopes, `hidden_if`. PostgreSQL is untested. |
| Record pickers (`RecordService.LookupRecords`) | Implemented: searches a Record Type by display label with keyset paging, hides cancelled and soft-deleted Records, resolves stored links by ID; the desk uses it for every Link field and a child Record's parent. Not yet used by Record Type fields, Records or the API (P4); no CLI command or UI, since it has no user-facing operation |
| PostgreSQL adapter | Later; not implemented and untested. The dialect interface exists so one can be added |
