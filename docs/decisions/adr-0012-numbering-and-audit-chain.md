# ADR-0012: Numbering series, the hash-chained Audit Log and request correlation
- **Status:** Proposed
- **Date:** 2026-11-19
- **Decision owner:** not assigned (awaiting project owner review)
- **Related decisions:** ADR-0006, ADR-0008, ADR-0011, spec sections 10.4, 12.1, 12.2, 24.3, 16.2 invariant 10, roadmap phase P6
## Context
A submittable document's `name` was a placeholder (its Record ID). The Record history stored only the keys of changed fields, so it could not show what changed, and nothing made it tamper-evident. A request ID existed on rows but was generated per write, so one click could not be tied to its audit rows and documents. Record pickers also asked people to type Record IDs.
## Options considered
1. **Database sequences for numbers.** Gap-free is impossible: a sequence value taken by a rolled-back transaction is lost. Rejected for statutory series (spec 24.3).
2. **Counter rows (chosen).** One row per series scope, locked with `SELECT ... FOR UPDATE` inside the submit transaction. A rollback returns the number.
3. **One chain per Record Type.** Smaller chains, but a cross-type deletion is harder to see and verifying costs a walk per type. Rejected for now.
4. **One chain for the data-change log (chosen).** A single head row serializes appends. Simple to verify and to anchor. Cost: every audited write waits for the previous commit.
5. **A hash per field row (spec 12.1 shape).** More rows. One row per change with a `changes` list keeps one hash per event and the same information.
## Decision (proposed)
- **Naming series.** A submittable document Record Type may set `naming_series`, such as `SINV-{yyyy}-{#####}`: literal text, the tokens `{yyyy}`, `{yy}`, `{mm}`, and exactly one counter token of 1 to 9 `#` (the counter is zero-padded and grows past its width). Each pattern with its date tokens filled in is its own counter, kept in `athena_number_counters`, so a year token restarts the series each year. Company and branch scopes arrive with the company master (P11); until then the scope is the date. Counter rows are locked through the dialect (`ForUpdate`).
- **When a number is taken.** At submit. A draft keeps the Record ID as `name`. `gap_free: true` takes the number inside the submit transaction, so a failed submit (a rejecting hook, a failed write) gives it back and concurrent submits take turns. `gap_free: false` takes it in its own short transaction: numbers may skip after a failure, writers never wait on each other. The audit row of the submit lists `name` with its old and new value.
- **Permanent names.** A document that already has a name of its own keeps it: manual names and amended documents (`<root>-1`, `<root>-2`). No RPC accepts a `name` change, and `name` is a reserved field key. If the next number is already used by a manual name the submit fails with a message that names it; the series does not skip it, because that would break gap-free numbering.
- **Manual override.** `allow_manual_name: true` lets `CreateRecord` carry `name`. The name must be unused, at most 140 characters and must not look like a Record ID. The create writes an extra `name_override` Audit Log row. There is no permission check until P8, so "privileged roles" (spec 24.3) is not enforced yet.
- **Audit Log** (`internal/audit`, `athena_audit_log`, `athena_audit_heads`, migration 8). One append-only row per change: Record Type, Record ID, revision, action (`created`, `updated`, `deleted`, `submitted`, `cancelled`, `name_override`), a `changes` list of field, old and new value, actor, source (`api`, `cli`, `import`), `request_id`, time to the millisecond, `prev_hash` and `hash`. The hash is SHA-256 over the previous hash and every other column, length-prefixed; changes are hashed in a canonical re-encoding so the database's JSON formatting does not matter. Appends run in the change's own transaction after locking the head row, so a rolled-back change leaves no row and no gap.
- **Verification.** `audit.Verify` walks the chain and fails on a missing, reordered, edited or inserted row, and on a head that does not match the last row (a deleted tail). `SystemService.VerifyAuditLog` and `athena audit verify` run it and print the head as `seq:hash`. Keep that value elsewhere (a daily export) and pass it back as an anchor: the check then also proves the chain still holds that row. `athena audit anchor` verifies the chain and prints only the head as `seq:hash`, for a scheduled job to append to a file outside the database (for example `athena audit anchor >> anchors.log`). Nothing schedules it: that stays with the operator.
- **Old history.** Migration 8 copies every `athena_record_history` row into the chain in time order (source `import`; old rows know only the changed field keys, so they have no old or new values) in one transaction, then drops the old table and its writer.
- **Request correlation.** A ConnectRPC interceptor gives each call one request ID (a client may send its own UUID in `X-Request-Id`; anything else is replaced) and returns it in the response header. Kernel writes use it for the Record's `request_id`, the Audit Log row, the Document Version and the Activity row. Calls without the interceptor (the CLI) get one new ID per operation and source `cli`. The OpenTelemetry trace ID is not stored.
- **Pickers.** `RecordService.LookupRecords` returns `id`, `label` and `state` for a Record Type, filtered by label text, sorted by label with keyset paging (default 20, at most 50). Soft-deleted and cancelled Records are not listed. With `ids` it resolves those Records whatever their state, so a form can still label a stored link. The label is the Record Type's `label_field`, else the document name once numbered, else the first required text field, else the first text field, else the ID. Writes refuse a new Link value that points to a missing, soft-deleted or cancelled Record; a link already stored is not rechecked.
- **Not built.** Masking of sensitive fields in the log, retention and archival, partitioning, automatic anchoring, per-company or per-branch scopes, other naming forms (`by_field`, `expr`, `hash`, `prompt`, `singleton`), and the other logs of spec 12.1.
## Consequences
- Every audited write takes the head row lock for the rest of its transaction. Throughput of writes is bounded by commit latency, and `Verify` reads every row on each run, so its cost grows with the log. Scaling options, none built: per-Record-Type chains or a chain per company (smaller walks, a cross-chain deletion is harder to see), verifying only from the last anchor forward (cheap, relies on the anchor), and archiving old segments with a sealed head hash that the next segment starts from. Revisit when verification takes noticeable time or write contention shows in the head-row lock.
- The chain proves integrity only against someone who cannot also rewrite every later hash and the head. An exported anchor closes that.
- Audit rows hold field values, so they need the same permissions as Records (P8) and masking for sensitive fields.
## Revisit when
P8 (actors, permissions, privileged override), P11 (company scope for series), P9 (rule source in the log), Postgres parity (JSON text hashing is already engine-independent).
