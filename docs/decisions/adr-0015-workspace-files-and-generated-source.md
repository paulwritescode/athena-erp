# ADR-0015: Workspace files, and where generated source goes
- **Status:** Proposed
- **Date:** 2026-11-20
- **Decision owner:** not assigned (awaiting project owner review)
- **Related decisions:** ADR-0004 and ADR-0008 (Workspace directory), ADR-0012 (Audit Log), ADR-0014 (permissions), D-009, O-002, spec sections 12.1, 21, 23.1, 23.2 and 24, roadmap phase P8a
## Context
A Workspace is a directory (`athena.yaml`, `record_types/`, hooks, Packs) plus a database. The user requires file management for that directory through the desk, the API and the CLI. D-009 says dashboard-authored Record Types are intended to produce Go source for the developer workflow, and O-002 asks how dashboard and codebase definitions stay in step. Both were open: no destination, owner or conflict rule was decided, and no generator exists.
Facts: a running Go binary cannot load new Go source, so generated Go takes effect only after a build. A write endpoint for host files is dangerous on an unauthenticated server, so it needs ADR-0014 permissions. The Audit Log row stores the record id in a CHAR(36) column.
## Options considered
1. Generate into a separate source tree outside the Workspace. Keeps the Workspace clean, but splits one repository in two and hides generated files from Git review.
2. Generate into the Workspace under `generated/`, owned by the publisher, edited through the same file service. One repository, reviewable in Git, conflicts detected by content hash. Costs a rule for who may edit what.
3. Do not generate at all; store only definitions. Simplest, but drops the D-009 direction.
## Decision (proposed)
**File service.**
- `FileService` (ConnectRPC) and `athena files` manage text files in four folders of the Workspace directory: `record_types/`, `rules/`, `packs/`, `generated/`. Both call `internal/files`, so they apply the same checks.
- Paths are relative, lowercase, use `a-z 0-9 _ - .`, never start a segment with a dot, have at most 8 segments, and end in `.go .json .md .star .txt .yaml .yml`. Absolute paths, `..`, backslashes, encoded separators, uppercase and symbolic links are refused, and every disk access goes through `os.Root` as a second guard. `.git`, `.env*`, `athena.yaml`, `.athena/`, `storage/` and the temporary files are outside the folders or start with a dot, so they are never listed or readable.
- Content is UTF-8 text without NUL, at most 1 MiB, at most 1000 files. `.yaml` and `.json` files must parse. A Record Type file (`record_types/<key>.yaml`) must follow the spec 24 top-level keys, `record_type` must equal the file name, field names must be unique snake_case, and errors carry line numbers. `.star` files are stored and edited, never run here.
- A write needs the content hash the caller read (optimistic concurrency); an empty hash means create. Writes are atomic (temporary file in the same folder, then rename).
- Permissions: system permissions `files:read` and `files:write`, held by Roles and by owners. Write does not include read. The gate denies without them and writes the denial to the Access Log.
- History: the database keeps every revision with its content (`athena_files`, `athena_file_versions`, migration 10), across renames and deletes. Content found on disk that differs from the last revision (an edit outside Athena) is kept as an `external` version before the next change replaces it.
- Audit: each create, update, move and delete appends an Audit Log row (`athena:file`, the file id, action `file_*`) with path, old and new hash, size, actor, source and request ID, never content.
- Telemetry: one span per operation with the operation, request ID, a hashed path id, byte count, file count and outcome. No path, content or credential.
**Generated source (option 2).**
- Generated Go for a Record Type goes to `generated/<key>_gen.go` in the Workspace. The publisher owns every `*_gen.go`; the first line is `// Code generated by Athena. DO NOT EDIT.`
- Hand-written hooks live outside `generated/` (for example `hooks.go`) and are never overwritten.
- The publisher records the hash of each file it writes. Before it writes again, it compares the hash on disk. If they differ, someone edited the file: the publisher stops and reports a conflict, and never overwrites silently. Dashboard and codebase edits to a Record Type definition use the same rule on `record_types/<key>.yaml`.
- Generated Go takes effect only after a new build and restart. Saving a Record Type updates metadata and the table only.
- **Not built in this phase:** the generator, the publisher's recorded hashes and the conflict report. The file service lets people read and edit `generated/` today, with the same hash check.
## Consequences
- The Workspace is one reviewable repository. `generated/` changes show in Git.
- A server started with `athena serve` has no Workspace directory, so FileService answers "no Workspace directory".
- The file service gives a user with `files:write` the power to change Rule sources and generated Go that later phases run or compile. Treat the permission like `build`.
- External edits are detected when a file is listed, read or next changed, not by a watcher.
- Moving a file into `record_types/` validates it as a Record Type file first.
- The history table stores content, so it grows with edits. At most 1 MiB per revision.
## Revisit when
The generator is designed (P15 Pack build), a hosted deployment has no writable Workspace directory, or Packs need signed archives instead of loose files. Accepting this ADR resolves O-002 and D-009's open parts.
