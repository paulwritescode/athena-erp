# Athena ERP • Product and engineering playbook

20 November 2026 · Proposed revision of the Athena ERP Frontend Playbook v1.1 · Go, Starlark, MariaDB, ConnectRPC and Vue

**Build the first production candidate around one company buying, selling, returning and paying for stock, then closing its books.** This journey exercises almost every expensive architectural decision: identity, document flow, exact quantities and money, partial fulfilment, settlement, access control and historical reporting. The same Core can then support services, assets and manufacturing through Packs. A successful pilot ends with a controller explaining every closing figure and a storekeeper explaining every remaining unit.

## 1. Product boundary and vocabulary

| Term | Contract |
|---|---|
| Core | Trusted Go runtime. Owns the database transaction, authorization, type semantics, lifecycle, posting invariants and access to effectful services. One process serves the embedded Vue desk and typed ConnectRPC API. |
| Workspace | One operational database plus installed Packs, data, users, Settings and Overlays. “Create a project” in the brief means create a Workspace. A business Project for job costing is a Record Type in the Projects area. The parent filesystem directory is the home. |
| Pack, Module, Overlay | A Pack is an installable, versioned unit. A Module groups Record Types, Queries, Reports and navigation within a Pack. An Overlay holds declared Workspace-specific differences against a pinned Pack version. |
| Record Type, Record, Kind | A Record Type defines a table-backed form. A Record is one instance. The nine Kinds are Master, Document, Child, Ledger, Balance, Setting, Log, Snapshot and Meta. A document class can be posting, non_posting, work or batch. |
| Rule, Workflow | A Rule is Starlark code bound to an event. A Workflow defines business states, transitions and approvals. A submitted order may still be partly fulfilled. A business status never turns it back into an editable draft. |
| Role, Grant, Scope | A Role groups Grants. A Grant authorises an action on a Type, optionally subject to a row condition and field level. A Scope restricts the values an assignment may reach, such as Company A and Warehouse North. |
| Ledger, Balance, Voucher | A Voucher is the source document for postings. A Ledger records movements. A Balance summarises them at a stated cutoff and can be rebuilt. Financial truth belongs to the committed movements. |
| Query, Report, Report Run | A Query declares a typed read. A Report adds presentation, time basis, drill-down and delivery. A Report Run freezes the output, inputs and provenance of one execution. |

**Design opportunity.** Let an administrator click through a permission change and see exactly which documents it affects. Let a controller click a stock value and follow it to a receipt, freight allocation and accounting entry. Let a disconnected employee capture a count and see when the server accepts it. These are measurable product promises. The audit identifies the operator reports behind each one.

## 2. One engine from button to books

1. The desk requests effective definitions and allowed actions for the current Workspace, actor and revision. Both Build and View use the same field and permission contracts. Importers, jobs and integrations call the same application commands.
2. A command identifies its Workspace, Type, Record, expected revision, action and a client operation ID. Go derives the actor and authoritative Workspace from the session and server binding. A request ID traces an attempt; a durable operation ID recognises a retry across attempts.
3. Begin the transaction. Recheck authorization, old/new row scope, field masks, state transition, open period, business approval and line availability. Acquire locks on the affected source applications, inventory keys, series and open items in stable order. A period close uses the same concurrency barrier as posting.
4. The Rule reads the consistent input, resolves dated account mappings, tax, FX and UoM, and returns a posting plan. Show the same calculation on Preview, including resolved accounts, source lines, applied policy versions and rounding. Submit recalculates at the current revision. A changed plan requires review where approval depended on it.
5. Go validates balance by company and book in base currency, consistent transaction-currency legs where applicable, allowed accounts and dimensions, cost/quantity rules, allocation ceilings and protected control accounts. Write the voucher revision, business number, Ledger rows, Balance deltas, source applications, audit event, operation result and outbox in one transaction. A validation error leaves no committed business effects.
6. A worker delivers committed notifications, documents and integration messages. A crash between delivery and acknowledgement can cause redelivery. Each consumer stores its own event identity and result. External payment initiation additionally needs provider idempotency and status lookup before retrying an uncertain transfer. [AWS transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

**Retry contract.** Unique operation key within Workspace, actor/client and command; persist canonical payload hash. Same key and payload returns the prior result subject to the caller’s current access. Same key with different payload is a conflict. Also enforce a business uniqueness constraint per voucher revision/event/book so two independently keyed submits cannot double post. A network timeout after commit is resolved through operation status. A worker lease has expiry, fencing and bounded retries. Durable deduplication covers the supported offline and integration replay window. A historical business effect remains protected by its permanent identity.

**Corrections.** Drafts use optimistic revision checks and field-level error feedback. Submit freezes business facts. Explicitly allow only harmless, audited metadata edits after submission. Cancel mirrors *stored* amounts, FX and quantities; amendment creates a successor draft. If downstream delivery, settlement or payroll depends on a voucher, show the blocking chain and authorised correction path. For a closed period, preserve the original date and book a linked correction in an allowed period, or run a separately approved reopen/reclose. Preserve signed Report Runs through both paths. This removes the conflict between immutable movements and rewriting historical valuation rows in kernel §6.

**Rule host.** Keep the constrained expression language for predicates, filters and declarative fields. Treat the existing expression subset as the compatibility boundary. Version its supported syntax. Starlark handles validation, derivation, posting, reaction, scheduling, guards and transforms through distinct capability sets. A validation Rule can return field errors; a posting Rule can construct a plan; a reaction can request a draft or an outbox event. None gets a database handle or provider credentials. Supply an injected clock, exact money/quantity helpers, deterministic iteration order, bounded reads and a frozen dependency snapshot. Pin code/Pack hash and input revisions for replay. Limit steps, wall time, host allocations, rows and cascade depth. An interpreter instruction budget alone does not bound a Go builtin that reads a million rows. A change to a posting Rule needs fixture replay, a plan diff and named approval. [Starlark in Go](https://github.com/google/starlark-go)

## 3. Access an administrator can operate

Use the system Role names in the kernel. **Platform Administrator** is the core-level developer/operator Role. **Instance Owner** is the owner of a Workspace. **System Manager** is the delegated application administrator. The desk can explain those scopes beside their existing names. Build mode is a privileged session capability. A developer’s job title creates no production-data entitlement.

| Role | May do by design | Boundary the server enforces |
|---|---|---|
| Platform Administrator | Operate the Core and registry, deploy compatible releases, manage infrastructure and recovery operations | No default application-level business grants across Workspaces. Storage/backup operators may have technical access to plaintext depending on deployment; key custody, operator access logs and customer-owned hosting address that separate trust boundary. Support access is individually approved, scoped, expiring and attributed. |
| Instance Owner | Bootstrap the Workspace, configure identity, assign System Managers, approve Pack activation, appoint another owner or transfer ownership | Protected ownership operation with recent MFA, verified recipient acceptance and transactional last-owner check. Business actions follow assigned business Roles and period/approval controls. The draft Go owner shortcut needs reconciliation with this design. |
| System Manager | Create and deactivate ordinary users, assign delegable Roles and Scopes, initiate permitted resets, inspect delivery status | Cannot assign ownership/platform status, grant beyond delegation, alter a higher-privilege account’s recovery channel or bypass maker/checker. Role editing and Role assignment can be delegated separately. |
| Business Roles | Purchase User drafts POs, Receiving Clerk records receipts, Accounts Payable Clerk enters bills, Treasury Officer releases approved payments, Accountant reconciles | Company/branch limits, transaction amount limits, field masking and independent approvals apply. Business and access administration are separate assignments. |
| Auditor, Report Viewer, Integration Service, Guest | Read specifically scoped evidence, run approved Reports, execute a bounded integration, or access an explicitly public surface | Auditor gets explicit audit scope and redaction. Service identities have expiry/rotation and no interactive session. Guest starts with no business grants. |

### Create a user and assign access

1. Open **Access → Users → Create user**. Enter display name, login identifier, verified delivery destination where appropriate, and identity provider. Select **Add Role** and choose one or more Roles by name or job function. Pick Company, Branch, Warehouse or other Scope *on that assignment*. Offer active-from and expiry for temporary cover.
2. The preview reads, for example, “Receiving Clerk can create and submit Purchase Receipts in North. Cost price is hidden. Payment release is unavailable.” The admin can open the effective Grants, see conflicting duties, remove a Role chip, or save. No expression authoring is required for ordinary setup.
3. Save user, pending identity, scoped assignments, invite generation, audit and notification-outbox event atomically. Admin sees **Invited**, delivery outcome and **Resend invite**. Delivery failure leaves a recoverable pending account. Duplicate submissions return the same user. A repeated invitation invalidates its predecessor. A deleted/suspended identity cannot silently regain old grants on reinvitation.
4. On first local login the user proves possession of the one-time challenge, chooses and confirms their own password, enrols required MFA, then signs in. Only enrolment operations are permitted before completion. A verified federated user completes the provider’s first-use flow and links by verified issuer/subject; email alone cannot merge an existing account. The active desk appears after policy checks.
5. **Access → User → Security → Reset password** shows target, provider, delivery method and effect on sessions. Authorise the actor against that target, require recent verification for sensitive recovery, revoke target sessions and prior challenges, and enter **Reset required**. The user sets a new password through a short-lived single-use challenge. Administrative reset does not silently remove MFA. Record initiator, target, outcome and correlation. Neither admin nor log sees the permanent secret. [OWASP password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

**No mail relay.** For local self-hosting, a verified operator can hand the user a one-time activation code through a separately agreed channel. Store only its digest. Show it once, rate-limit attempts, expire it, and require the user to choose a password. Bootstrap the initial owner locally with a one-use setup operation guarded against competing initialisations. Document owner recovery separately from routine System Manager resets. Lost last-owner access needs a host-controlled, logged recovery procedure, immediate credential rotation and notification.

| Target auth operation | Storage and state transition | Caller-visible result |
|---|---|---|
| Create with scoped Role assignments | Invite-only identity plus versioned assignments. Unique normalised login per identity realm and Workspace membership pair | User ID, state and delivery status. Durable resend available. |
| Accept or complete first-login/reset challenge | Verify workspace, purpose, identity, expiry, unused digest and current generation. Atomically consume on successful completion. Password hash local only when using local identity | Ordinary session issued only after successful enrolment and any MFA. Two simultaneous completions yield one success. |
| Suspend / reactivate | Suspend invalidates tokens, sessions and outstanding grants in caches. Reactivate verifies assignments, dates and identity status | Previously open browser must reauthorise. Reactivation requires explicit review of privileged assignments. |
| Save Role / assign / revoke / transfer | Compare expected revision, check delegation on the entire proposed diff, record old/new, invalidate policy generation and optional queued deliveries | Effective access explanation and new revision. A stale administrator sees the conflict. No partial role update. |

**RPC evolution.** Extend the draft CreateUser contract for an invite-only request with no permanent password and a separate completion command. Deprecate administrative permanent-password fields in CreateUser/ResetPassword, retain Protobuf field numbers as reserved after removal, and return a distinct recovery/enrolment state in the session contract. Migrate existing active users without forcing everyone through first use. Existing temporary-credential accounts require an explicit migration flag. Gate every service through the production server registration and exercise the real Vue client. Keep authentication provider details outside Grant evaluation.

**Local identity baseline.** Follow the repository’s P8 design for Argon2id password hashing, server-side sessions, HttpOnly/SameSite cookies and CSRF checks. Require TLS and Secure cookies on remote deployments. Rotate the session at authentication or elevation, enforce idle and absolute expiry, and bind completion to a verified identity and Workspace. Rate-limit enrolment, login and recovery. Use the same public recovery response for existing and unknown users; surface delivery details only to an authorised administrator. Require MFA for privileged recovery and let authorised users manage their own sessions.

### Select permissions without writing code

**Access → Roles → New or Duplicate → select Module → select Record Type.** Toggle supported actions (Read, Create, Write, Submit, Cancel, Amend, Approve, Print, Export and declared custom actions). Pick field permission level, “only own Records”, named Scope and an approval band from selectors. Advanced predicates are available to authorised policy authors through validated, previewable expressions. **Save** presents the diff, affected users, conflicts and assignment scope. A failed save keeps the local draft. A managed Role edit becomes an Overlay, a clone becomes a custom Role. A Pack update that expands access shows an explicit privilege diff before activation.

**Evaluation.** Identify the active Workspace membership. For each eligible Role assignment, require that its Grant covers the action and Type, its row condition is true, its own assignment Scope matches, and its field level covers the requested fields. Union the results of *whole matching assignments*. Intersect with user-wide restrictions. Then enforce workflow, segregation of duties, period policy, protected fields and account status. An unscoped assignment is an explicit privileged choice. An empty required Scope denies. Apply predicates before joins, paging, totals, graph counts and export. Recheck on update against both old and proposed rows. Lookups, counts, attachments, report schedules, background jobs, CLI and direct RPC use the same authorization service. Bind cached decisions to policy version and Workspace.

**Counterexample.** A user is Receiving Clerk in North and a read-only Auditor in South. They can see both locations under their respective assignments and can receive only in North. A naive union of all actions and all locations would let them receive in South. The Permission Explorer should show which assignment matched each action and why South submit failed. A staff member with a second Role permitting approval still cannot approve their own expense where the Workflow requires an independent reviewer. Two managers concurrently removing the last owners must leave at least one active verified owner.

## 4. Reports, published evidence and logs

Every Report definition names its grain, source, dimensions, sign convention, currencies, posting states, cutoff, required Grants, excluded rows and drill-down. The Query compiler filters at source and validates joins before aggregation. Joining invoice lines to multiple settlements directly multiplies sales. Aggregate each to invoice grain first or use a typed allocation join. A saved view stores filters and presentation preferences; publishing one grants no new data access.

| Report available to the relevant Pack | Time basis and calculation | Drill-down and control |
|---|---|---|
| Trial balance, general ledger, P&L, balance sheet, cash flow | Trial balance shows opening + debit − credit = closing. P&L measures period activity. Balance sheet is as of date. Cash flow classifies actual cash movements and reconciles opening/closing cash. | Account → dimension → posting group → voucher/line. Group by company/book/base currency before any consolidation. Unmapped cash-flow categories go to exceptions. |
| Receivables and payables ageing | Per instalment at as-of date, invoice less allocations and credits effective through that date. Bucket by due date in company timezone. Keep unallocated advances separate. | Party → instalment → invoice → receipts/credits. Sum agrees with the control account, including separately explained credits/advances. |
| Stock balance, valuation and stock-to-GL | On-hand sums signed quantities by owner, item, location and lot. Available excludes active reservations and non-saleable stock under policy. Value follows layers and cost adjustments at cutoff. | Warehouse → lot → source receipt → issue/cost application → GL. Show rebuild watermark and exception rows. |
| Open orders, PO match and GRNI | Open quantities per line, received less billed at receipt value, separate quantity and price exceptions. Unconfirmed service lines tracked separately. | PO line → receipts → invoice applications → match policy and reviewer. Equal header totals cannot hide residuals. |
| Expenses and asset register | Claims by incurred/posted date, employee payable and uncleared advances. Asset register shows opening cost, additions, disposals, depreciation, impairment and closing net book value by book. | Expense → advance and reimbursement. Asset → schedule, posted run and disposal. Tie to corresponding GL accounts. |
| Manufacturing, projects and people | Material yield/scrap, WIP and variance per order. Project cost and billed margin per task and time basis. Leave as-of and payroll liabilities by period. | Compare lot genealogy or cost inputs to output. Enforce payroll field restrictions even on group totals and exports. |
| Tax, budget, audit and close | Taxable bases and tax amounts by jurisdiction/return period; approved budget less commitments and actuals. Closing Pack records tie-outs, outstanding exceptions and sign-offs. | Drill to tax line, commitment release or audit reason. Statutory layouts and filing adapters require validated country Packs. |

**Report Run contract.** Capture definition/Pack/Rule hashes, normalised parameters, date basis, timezone, effective data cutoff and ledger high-water mark, requester/service, effective Scope, locale, currency, row count and protected object digest. Distinguish “what transactions are effective by 31 March?” from “what did we know when we closed on 2 April?”. Use a transactionally consistent snapshot or versioned source/cutoff for every join; a timestamp on an unversioned mutable master cannot reproduce yesterday’s result. Freeze display labels and applied rates that affect output. Show generated time, effective date and freshness separately on screen and in export.

**Automatic generation.** A schedule names timezone, calendar, parameters, recipients, format and owner. Decide what happens across DST or missed runs. Uniqueness on schedule + logical period + intended run prevents duplicate daily statements after restart. Worker checks current Grants at execution and each recipient’s current Scope at delivery/download. Deliver an authenticated link by default and keep published artifacts private. Old runs remain immutable; revoked readers lose access. Log skips, failures and retries. One recipient’s wider access never determines another recipient’s file. Large jobs run asynchronously with progress, cancellation and bounded exports.

| Evidence stream | What it records | Access, retention and recovery |
|---|---|---|
| Audit Log, Document Version, Activity Timeline | What changed, by whom, reason, source, before/after at permitted field level, revision and request ID. Timeline adds assignments, comments and transitions. | Commit the business audit event with the write. Redact sensitive fields by schema. Keep redaction consistent on old versions. Timeline shows only evidence the viewer can read. |
| Posting Log, Rule Run | Voucher/line, plan hash, versions, affected Ledgers, totals, invariant result, injected time, bounded resource use, failure code | Trace a number to its inputs. A rejected attempt can be recorded separately after rollback. Never describe an attempted movement as committed. |
| Access Log, Migration and Config Log | Invites, reset, revocation, sensitive reads/exports, permission diffs, support session, migration checkpoint and installation history | Restricted readers; no tokens, passwords or raw authentication payloads. Periodic digests anchored with independent custody improve tamper detection. Verify chain after restore. |
| Job Run, Integration Log, Notification Log | Durable operation/event ID, delivery attempt, lease, destination alias, response category, retry time, outbox lag and terminal state | Replay by event ID with deduplication. Redact provider bodies. An operator can recover a pending send without resubmitting an invoice. |
| Request Log, Integrity and Incident Log | Correlation, route, latency, error class, data cutoff, violated control, expected/actual and owner of resolution | Technical telemetry is optional. Business audit and reconciliations continue when telemetry is off. Record resolution with reason and corrective voucher. |
| Report Run and Closing Pack | Frozen evidence, checksums, scope, sign-offs and cross-report controls | Retention by Workspace, jurisdiction and evidence class. Legal holds suspend expiry. Restrict payroll/PII evidence to its authorised archive. |

Treat a chain of hashes as integrity evidence subject to who controls the chain and its anchor. Back up anchors separately, apply retention to exports and document archive retrieval. Monitor posting failures, reconciliation residuals, close-blocking jobs, undelivered invites, outbox age, scoped-query latency and restore test results. Each alert should identify the affected Workspace, cutoff and recovery action without including business values in telemetry.

## 5. PWA and intermittent connectivity

The first offline job is a storekeeper counting assigned stock in a warehouse with patchy coverage. Before leaving coverage, they download an authorised count sheet. They scan quantities, close and reopen the app, return to coverage and submit the draft for reconciliation. The supervisor sees who counted what, at which cutoff, and which movements happened during the count. Success is a discrepancy the supervisor can explain. Installation on the home screen alone proves little about this workflow.

| Capability | Proposed behaviour |
|---|---|
| Install and launch | Serve HTTPS, an app manifest with stable ID, start URL, scope, icons and standalone display, plus a service worker and versioned offline shell. Test browser and installed modes on actual supported Android, iOS and desktop browsers. Provide platform-appropriate installation instructions. [MDN installation requirements](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) |
| Offline read and capture | Opt-in per Workspace and trusted device, tightly scoped lookup snapshot with freshness/expiry. Store count lines and explicitly allowed expense drafts in IndexedDB. Capture actor, Workspace, draft UUID, original Record revision, schema version, count cutoff, units and stable line IDs. No sensitive-report or payroll cache. Use a restricted shared-terminal mode with offline storage disabled. |
| Operations requiring the server | Financial posting, final stock availability, payment release, approvals, password changes, role edits and period close require current server authorization. The screen distinguishes **Saved on this device**, **Awaiting sync**, **Needs review** and **Accepted by server**. Printing a local draft marks it as such. |
| Sync | Use a persistent ordered queue with one writer per device/account, stable operation IDs, dependency IDs for new parent/children, bounded retries and foreground **Sync now**. Background Sync is opportunistic and its browser support varies. Upload evidence privately, verify digest, then link to an accepted draft. [MDN Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API) |
| Conflict resolution | The server checks session, Grants, current Type, revision and count baseline on every replay. Duplicate same payload returns the original draft. Changed upstream fields show a side-by-side diff. Show stock movement since count cutoff. Require supervisor approval for a variance; never add a resubmitted absolute count to the ledger. |
| Storage and upgrades | Cache hashed public shell assets only in Cache Storage. Keep private drafts in a user/Workspace-specific store, enforce offline expiry, minimise sensitive data and purge on logout/account switch under a documented unsynced-work policy. Offer to sync or knowingly discard before voluntary logout. A disconnected device cannot receive instant revocation. Browser eviction/private browsing can erase local-only work. Warn on quota pressure, request persistence where supported, and show the count of unacknowledged drafts. [MDN storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) |

Service-worker upgrades must activate compatible code only after a transactional queue-schema migration; a failed migration leaves recoverable drafts and an actionable status. When a rollout removes a field, submit using a supported previous command version or route to manual remapping. Do not cache session responses, ConnectRPC reads, signed URLs or privately generated documents at the edge. A lost device with unsynced drafts is a real recovery limit. A business requiring guaranteed offline custody needs managed-device protection and a separately qualified local storage/backup design.

**Acceptance run.** Download a 12-line count, scan three serials, disconnect, restart, edit one count and reconnect with Background Sync disabled. Interrupt after the server commits but before acknowledgement. Retry in the foreground. Expect three identities once, one accepted draft and the same server ID. Repeat after Role revocation, Workspace switch, a competing stock issue and a Pack upgrade. Expect denial, isolation, variance review and schema resolution respectively. No stock or GL movement occurs until authorised review and posting.

## 6. Deployment and service integrations

Ship one self-hosted path that can complete the worked trading scenario using the Go binary, MariaDB, local private files, local identity and a database-backed job worker. The workspace can run on a LAN with no paid cloud account. The operator owns database and attachment backups. A managed deployment may replace one dependency at a time. Publishing signed Packs, a hosted notification service or a cloud identity provider must never be prerequisites for reading a customer’s own books.

**Choosing a deployment.** A single-site pilot with local IT can start with the self-hosted profile and off-site encrypted backups. A multi-branch company without database operations staff can use managed MariaDB and private object storage while retaining the same posting path. Companies with established identity should connect their IdP first and import membership explicitly. Add a second datastore only when measured read load, an external system requirement or retention constraints justify its ongoing cost. To compare quotes, price the same workload: Workspace count, peak concurrent posters, attachment GB/month, read/write requests, retained versions, restoration copies, identity usage, transfer and operator time. Capture region, retention and workload assumptions with any later price estimate.

**Portability proof.** Export a versioned Workspace manifest, Pack locks, schema versions, reference keys, audit anchors, open items, Ledger facts, users’ stable external references and an attachment manifest. Keep credentials in a separately protected recovery system. Restore to an isolated target, remap provider identities after verification, verify hashes of private files and compare control accounts. Disable outgoing bank, payroll, email and tax deliveries during restore. Fence or retire the old writer before cutover. Compare the recovered event checkpoint with external provider acknowledgements before resuming queues.

## 7. Deployment, migration and open-source release

**First install.** Guided setup collects company and accounting inputs once, explains required fields in business language, offers the Business starter and shows exactly which Records are ready. Offer an installable sample Workspace separately. A nontechnical owner should reach “Invite a colleague”, “Create first Item” and “Enter opening balances” without opening Build mode. Provide a health page with actionable readiness checks for DB, storage, identity, background delivery, clock/timezone and unapproved ledger mappings.

**Switching from another ERP.** Map external IDs for masters, merge duplicate parties after review, import dated exchange/UoM mappings, then stage open customer/supplier instalments, serial/lot and valuation layers, assets by book and open commitments. Post opening balances as a balanced batch against an opening clearing account. Avoid posting control balances twice when subledger openings already contribute to the GL. Reconcile trial balance, AR/AP by currency and due date, stock quantity/value by warehouse, asset carrying values and bank totals. Clear the opening clearing account. Obtain sign-off, freeze legacy input, apply the signed delta and keep a read-only legacy archive or imported evidence for pre-cutover detail. Run a parallel close and compare differences before making Athena the authoritative system.

**Pack upgrades.** A manifest pins API version, dependencies, supported dialect, capabilities, Role/Grant templates, migration IDs, seed revisions, tests, publisher and licence. Verify signatures and content hashes, resolve dependencies, preview changed fields, destructive operations, grants and Overlay conflicts. Use an expand/backfill/validate/contract sequence for live data. Record checkpoints and use a Workspace lock around cutover. A Pack version downgrade is safe only with a compatible schema/data contract. A restore rolls back later business writes too, so quiesce, preserve the post-backup delta and rehearse replay before using it as rollback. Offer a downloadable preview and migration log.

**Open-source deliverable.** Publish Core, the usable starter Packs, format definitions, build steps and conformance fixtures under explicitly chosen OSI-approved terms. Apache-2.0 is a candidate if broad downstream integration is the priority. The maintainer still needs to select the licence and confirm rights for dependencies, fonts, icons, seed data and country templates. Provide a public security contact, contributor guide, migration/deprecation policy, signed release checksums, SBOM and a testable restore procedure. A registry can serve a signed local mirror; self-hosted installations must be able to install verified local Pack archives and export their data without vendor credentials. ### Delivery gates

Each gate below is a product acceptance milestone spanning several engineering phases. The repository roadmap §8 records a kernel-first decision covering P0–P22. P8 is local authentication, P8a Workspace files, P9 the Starlark host, P11–P14 the ledger/report foundation, P15 Pack packaging and P17–P18 stock. P23 is the separately gated catalogue implementation. This research specifies what those first-party Packs must contain. Use test-only business fixtures during kernel development; make the clean-install Business starter available when the catalogue ships. The recorded P11 boundary gives Core only company, currency, fiscal year and dimension masters. SQL engine parity, customer-facing cloud deployment and statutory coverage each need their own evidence.

**Generated form behaviour.** Keep exact values as strings/typed structures until formatted; parse with the form locale, persist canonical values. Zod provides immediate shape and required-field feedback. Go owns link validity, exact arithmetic, authorisation, effective-date checks and cross-row constraints. Child tables support add, reorder, remove and keyboard navigation within the parent. View mode exposes Created from, Creates, Related, Activity, owner, revision, posting date, request reference and last modification. Hide or mask restricted fields consistently in old versions and print layouts. A server conflict preserves unsaved changes and offers reload or a deliberate reapply after diff.

**Lifecycle controls.** Draft supports Save, Submit and permitted draft deletion. Submitted supports approved metadata changes and Cancel where allowed. Cancelled is read-only and may expose Amend. A linked successor is navigable from the original. Show business status independently, for example “Submitted · Partly paid”. Explain a disabled action when the user may learn the reason, such as missing posting account, unapproved variance or a closed period. Remote permission changes can invalidate a visible action. The server’s denial must recover cleanly.

**Everyday operations.** Command palette results include only readable Records, Reports, permitted actions and accessible settings. Saved views can be personal or shared. Personal filter and sort preferences never broaden another user’s access. Import offers column mapping, per-row errors and a server-validated dry run. Notifications have read/unread state, opt-in digests, deduplication and safe deep links. Comments and mentions inherit Record visibility. Time-sensitive confirmations state the quantity, amount, period or session impact. Sonner handles immediate feedback; queued jobs, posting failures and invitation delivery retain durable status after the toast disappears.

**Developer entry.** Require an authorised build capability, recent authentication with the required assurance and an expiring elevation session. In production, reviewed Pack deployment may be the only permitted definition change. Build/View uses one theme, field schema and permission service. A simulation of another Role is a read-only explanation over permitted examples. A support operator viewing customer data requires a distinct authorised assignment.

### First-day usability trial

Give an owner and a storekeeper a clean Workspace. Ask the owner to set up a company, invite the storekeeper for one warehouse, recover their access, and explain whether they can see cost prices. Ask the storekeeper to receive part of an order and locate what remains outstanding. Ask the accountant to return one item and explain the closing stock value. Observe wrong turns, errors requiring outside help, time to first accepted transaction and whether the participants can distinguish saved, submitted and posted. Use the same tasks and starting data for comparative testing. Publish the test protocol and measured outcomes with any future ease-of-use claim.
